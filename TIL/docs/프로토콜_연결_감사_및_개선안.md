# AgriBot 프로토콜 연결 감사 및 개선안

기준일: 2026-04-02

## 요약

이번 정리는 "동작은 하지만 임시 연결이 섞여 있던 경로"를 우선순위로 바로잡는 데 집중했다.

- `backend <-> ROS` 제어 plane:
  - 기존: shared JSON file bridge
  - 개선: typed ROS topic direct bridge를 primary로 추가
  - QoS: `protocol_qos.yaml`로 primary topic QoS 정책 명시
  - fallback: 기존 runtime file bridge 유지
- `backend -> IoT` 제어 plane:
  - 기존: `ros2 topic pub` subprocess
  - 개선: backend process 내부 direct ROS publisher를 primary로 추가
  - fallback: 기존 subprocess 유지
- `ROS /iot/command_result`:
  - 기존: `std_msgs/String + JSON`
  - 개선: `agribot_interfaces/msg/IoTCommandResult`
- `ROS <-> MQTT`:
  - 기존: 단순 publish/subscribe, reconnect/offline queue 정책 부재
  - 개선: broker policy 파일에 reconnect backoff / publish retry / disk offline queue 추가
- `Frontend <-> Backend WebSocket`:
  - 기존: echo stub
  - 개선: live snapshot stream으로 교체

## 연결별 평가

### 1. Frontend <-> Backend

- HTTP/JSON:
  - 상태: 적합
  - 비고: 화면 데이터 조회/명령 요청 용도로 적절
- WebSocket `/ws/live`:
  - 기존 문제: 실데이터 없이 echo 동작만 수행
  - 조치: backend가 direct ROS bridge 상태와 fallback 상태를 주기적으로 push하도록 변경

### 2. Backend <-> ROS

- 기존 구조:
  - `robot_command_bridge_service`, `mission_bridge_service`가 JSON 파일을 runtime dir에 기록
  - ROS executor가 파일을 polling
- 문제:
  - 제어 plane이 파일 polling에 의존
  - transport 상태를 런타임에서 관찰하기 어려움
  - backend가 ROS graph subscriber 유무를 직접 확인하지 못함
- 조치:
  - `RobotCommand`, `MissionRequest`, `RobotCommandStatus`, `RobotControlState`, `MissionBridgeStatus` 인터페이스 추가
  - backend process 내부 `ros_protocol_bridge.py` 추가
  - backend는 direct ROS subscriber 존재 시 typed topic으로 발행
  - `agribot_bringup/config/protocol_qos.yaml`로 direct topic QoS 정책을 파일로 고정
  - subscriber가 없거나 ROS 환경이 없으면 기존 file bridge로 fallback

### 3. Backend -> IoT

- 기존 구조:
  - payload JSON 파일 생성
  - `publish_iot_command.py` 서브프로세스로 1회성 publish
- 문제:
  - backend가 ROS node로 직접 붙지 않음
  - subprocess 실패/timeout이 transport 레벨의 본질적 상태와 섞임
  - manual sprinkler 명령이 guard를 우회해 `/iot/commands/dispatch`로 직접 들어가던 경로 존재
- 조치:
  - backend direct ROS publisher를 primary로 추가
  - subprocess path는 fallback으로 유지
  - manual 명령은 장치 종류와 무관하게 `/iot/commands/manual`로 통일
  - auto 명령만 `/iot/commands/auto` 사용

### 4. ROS internal IoT result/status

- `/iot/device_state`:
  - 상태: typed message로 적절
- `/iot/command_result`:
  - 기존 문제: `std_msgs/String + JSON`
  - 조치: `IoTCommandResult.msg`로 타입화

### 5. ROS <-> MQTT

- 기존 문제:
  - reconnect/backoff/offline queue 정책 부재
  - device state / command result topic이 단일 topic에 몰림
  - contract 문서는 있었지만 broker 동작 정책이 코드/설정에 충분히 반영되지 않음
- 조치:
  - `mqtt_topics.yaml`에 broker policy 추가
    - `clean_session`
    - `reconnect_min_delay_sec`
    - `reconnect_max_delay_sec`
    - `publish_retry_count`
    - `publish_retry_backoff_sec`
    - `offline_queue_dir`
    - `offline_queue_max_messages`
  - topic template 정리
    - `agribot/iot/device_state/{device_id}`
    - `agribot/iot/command_result/{command_id}`
  - inbound manual command canonical topic 추가
    - `agribot/commands/manual`
  - legacy alias 유지
    - `agribot/commands/actuation`

## 남겨둔 레거시 / 후속 정리 대상

- `patrol/status`, `harvest_route/status`는 아직 `std_msgs/String + JSON` 기반이다.
  - 이번 변경에서는 backend 경계와 IoT result 경계를 우선 정리했고,
  - ROS internal 상태 토픽 타입화는 2차 리팩터링 대상으로 남긴다.
- `runtime_snapshot_exporter`가 만드는 pose/path snapshot 파일은 여전히 존재한다.
  - 이는 현재 제어 plane이 아니라 시각화/preview artifact 성격이므로 fallback/preview 용도로 유지했다.

## 운영상 기대 효과

- backend가 ROS subscriber 유무를 기준으로 direct path와 fallback path를 선택한다.
- manual/auto/dispatch 흐름이 장치별 예외 없이 일관된다.
- MQTT broker 일시 장애 시 메시지가 디스크 큐로 보존된다.
- `/iot/command_result`와 WebSocket live stream이 더 이상 "문자열 페이로드"나 "스텁 연결"에 머무르지 않는다.
