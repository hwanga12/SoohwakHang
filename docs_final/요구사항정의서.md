# AgriBot 요구사항정의서

## 1. 문서 개요

### 1.1 목적

이 문서는 현재 저장소의 실제 구현을 기준으로 AgriBot 시스템의 요구사항을 다시 정리한 문서다. 기획 초안이 아니라 현재 동작하는 밭(`farm`) 운영 구조를 기준으로 작성한다.

### 1.2 작성 기준

- 기준 시점: `2026-04-02`
- 기준 코드: `backend/`, `agribot_ws/`, `frontend/`
- 운영 환경: `farm_world`
- 문서 범위: 운영 API, 로봇 제어, AI 판단, IoT 제어, 수확 이력

### 1.3 제외 범위

현재 구조에서 다음 항목은 공식 범위에서 제외한다.

- 온실 전용 설비 제어
- 사용자 인증/인가
- 범용 알림 센터
- 완전한 실시간 이벤트 푸시 WebSocket

## 2. 시스템 정의

### 2.1 시스템 목표

AgriBot은 밭 환경에서 작물 상태를 관찰하고, 병해와 숙도를 판단하며, 필요한 경우 로봇 미션과 IoT 장치 제어를 연동하는 통합 운영 시스템이어야 한다.

### 2.2 주요 사용자

| 사용자 | 역할 |
| --- | --- |
| 운영자 | 대시보드 조회, 로봇 명령, 미션 실행, 장치 제어, 알림 확인 |
| 로봇 런타임 | 순찰, 이동, 정지, 복귀, 수확 미션 수행 |
| AI/인지 서비스 | 병해 판단, 숙도 판단, 수확 판단 생성 |
| IoT 제어 계층 | 급수, 영양제, 스프링클러 상태 반영 및 명령 수행 |

### 2.3 현재 운영 장치

- `farm_01_watering`
- `farm_01_nutrient`
- `sprinkler_0`
- `sprinkler_1`
- `sprinkler_2`
- `sprinkler_3`

## 3. 아키텍처 요구사항

| ID | 요구사항 |
| --- | --- |
| `AR-01` | 백엔드는 FastAPI 기반 REST API를 제공해야 한다. |
| `AR-02` | REST API 기본 prefix는 `/api/v1` 이어야 한다. |
| `AR-03` | 실시간 연결 경로는 `/ws/live` 를 유지해야 한다. |
| `AR-04` | 대부분의 REST 응답은 `{"data": ...}` envelope를 사용해야 한다. |
| `AR-05` | 로봇 제어는 JSON 파일 브리지 기반으로 런타임과 연동해야 한다. |
| `AR-06` | 로봇 명령과 미션은 중복 방지를 위해 `command_id` 또는 `mission_id` 를 지원해야 한다. |
| `AR-07` | 런타임 상태 파일이 존재하면 DB보다 런타임 상태를 우선 사용해야 한다. |
| `AR-08` | IoT 수동 제어는 사용자 관점의 논리 명령과 장치 관점의 실제 dispatch 명령을 분리해야 한다. |

### 3.1 장치 명령 변환 규칙

| 장치 종류 | 사용자 논리 명령 | 내부 dispatch 명령 |
| --- | --- | --- |
| `WATER_PUMP` | `WATERING` | `dispense_water` |
| `NUTRIENT` | `NUTRIENTS` | `apply_nutrient_recipe` |
| `SPRINKLER` | `WATERING` | `spray_water` |
| `SPRINKLER` | `NUTRIENTS` | `spray_nutrient_solution` |

## 5. 데이터 요구사항

### 5.1 영속 엔티티

시스템은 다음 영속 데이터를 관리해야 한다.

| 엔티티 | 설명 |
| --- | --- |
| `zones` | 운영 구역 |
| `robots` | 로봇 현재 상태 |
| `plants` | 식물 기준 정보 |
| `fruits` | 과실 기준 정보 |
| `missions` | 로봇 미션 이력 |
| `crop_observations` | 병해/관측 기록 |
| `environment_samples` | 환경 센서 이력 |
| `iot_devices` | 장치 마스터 및 현재 상태 |
| `actuation_commands` | 장치 제어 명령 |
| `actuation_logs` | 장치 실행 결과 |
| `alerts` | 운영 알림 |
| `ai_judgments` | AI 판단 결과 |
| `harvest_events` | 수확 이벤트 |

### 5.2 파생 또는 비영속 데이터

다음 항목은 현재 구현에서 별도 ORM 엔티티가 아니다.

| 항목 | 설명 |
| --- | --- |
| `actuation_recommendations` | 환경값과 식물 상태를 기반으로 생성되는 파생 추천 |
| `media_assets` | 파일 시스템 기반 이미지 조회 대상 |
| 로봇/미션 상태 파일 | JSON 파일 브리지 기반 런타임 authoritative 상태 |

## 6. 인터페이스 요구사항

| 구분 | 요구사항 |
| --- | --- |
| 프론트엔드 | REST API와 WebSocket으로 데이터를 조회해야 한다. |
| 로봇 런타임 | 로봇 명령은 JSON 파일 브리지로 전달되어야 한다. |
| 로봇 런타임 | 제어 상태와 미션 상태는 런타임 상태 파일 우선 정책을 따라야 한다. |
| MQTT/IoT | 환경 데이터와 장치 상태는 MQTT bridge와 ROS 제어 노드를 통해 연동 가능해야 한다. |
| 장치 제어 | 장치 종류와 논리 명령이 맞지 않는 요청은 거부해야 한다. |

## 7. 비기능 요구사항

| ID | 요구사항 |
| --- | --- |
| `NFR-01` | API 경로는 `/api/v1` 버전 계약을 유지해야 한다. |
| `NFR-02` | 도메인별 JSON 응답 구조는 일관성을 유지해야 한다. |
| `NFR-03` | 파일 브리지 기반 명령은 식별자 기반 중복 방지를 지원해야 한다. |
| `NFR-04` | 런타임 파일과 DB 간 데이터 출처가 다르더라도 동일 의미의 응답을 제공해야 한다. |
| `NFR-05` | 파일 응답 API는 대상 파일이 없을 경우 `404`를 반환해야 한다. |
| `NFR-06` | 브리지, 모델, 외부 런타임 의존성이 없으면 `503` 또는 적절한 오류를 반환해야 한다. |
| `NFR-07` | 현재 인증 기능이 없으므로 운영망 또는 별도 게이트웨이 보호를 전제로 한다. |

## 8. 수용 기준

- 운영자는 대시보드, 구역, 식물, 알림, 환경, 장치 상태를 조회할 수 있어야 한다.
- 운영자는 로봇 정지, 재개, 이동, 복귀, 순찰, 수확 명령을 요청할 수 있어야 한다.
- 운영자는 급수와 영양제 수동 명령을 생성하고 결과를 이력으로 확인할 수 있어야 한다.
- 병해 라벨과 좌표가 주어지면 스프링클러 처리 계획 계산과 dispatch를 수행할 수 있어야 한다.
- 시스템 문서는 현재 구현의 ORM 구조와 라우터 계약을 반영해야 한다.
