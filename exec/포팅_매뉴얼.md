## 5. 배포 시 특이사항

1. `scripts/agribot_env.sh`는 실행이 아니라 반드시 `source scripts/agribot_env.sh`로 불러와야 한다.
2. Backend와 ROS 노드는 반드시 같은 `AGRIBOT_RUNTIME_DIR`를 바라봐야 한다. 이 값이 다르면 프론트 버튼은 눌리지만 실제 상태 파일이 갱신되지 않는다.
3. Frontend는 Backend가 정적 파일을 서빙하지 않는다. 현재 저장소 기준 배포는 `npm run dev` 기반이며, 별도 운영 웹서버(Nginx/Apache) 설정은 포함되어 있지 않다.
4. Backend CORS 허용 origin이 `http://localhost:5173`, `http://127.0.0.1:5173`로 하드코딩되어 있다. 원격 배포 시 `backend/main.py` 수정이 필요하다.
5. `scripts/backend_up.sh`는 PostgreSQL, Mosquitto, pgAdmin 컨테이너를 먼저 띄우고, 기존 Uvicorn 프로세스 및 포트 점유 프로세스를 종료한 뒤 재기동한다.
6. `scripts/frontend_up.sh`도 기존 `5173` 포트를 점유한 프로세스를 종료한 뒤 Vite dev server를 올린다.
7. `scripts/agribot_launch.sh`는 이전 시뮬레이션 잔여 프로세스를 정리하고, launch 파일이 `runtime_dir` 인자를 지원하면 자동으로 `runtime_dir:=${AGRIBOT_RUNTIME_DIR}`를 주입한다.
8. 병해 모델은 기본적으로 `artifacts/models/tomato_disease/v1/best.pt`를 찾는다. 다른 경로를 쓰면 `AGRIBOT_TOMATO_DISEASE_MODEL_PATH` 또는 `AGRIBOT_TOMATO_MODEL_PATH`를 지정해야 한다.
9. 발표/시연 전에는 `./scripts/operator_runtime_health.sh --reset-runtime` 또는 `rm -rf "$AGRIBOT_RUNTIME_DIR"`로 런타임 파일을 초기화해야 이전 상태가 남지 않는다.
10. 현재 하드코딩 맵 기반 자율주행 모드에서는 LiDAR obstacle layer와 정적 맵 정렬 이슈 때문에 obstacle layer를 비활성화하는 운영 전제가 있다. 즉, 데모/포팅 시 live obstacle 회피까지 기대하면 안 된다.
11. DB 접속 정보는 개발용 기본값(`agribot/password`)으로 고정돼 있으므로 실제 운영 환경에서는 별도 시크릿 관리가 필요하다.

```bash
docker exec backend-postgres-1 pg_dump -U agribot -d agribot_db --clean --if-exists --inserts > exec/db/agribot_db_dump_20260330.sql
```

- 비고:
  - plain SQL dump 형식
  - `DROP ... IF EXISTS` + `INSERT` 포함
  - 현재 실행 DB 데이터 상태를 그대로 백업한 최신본
