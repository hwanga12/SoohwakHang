# 🌱 AgriBot 프로젝트 전체 기획서

스마트 농장 자율주행 채소 관리 로봇의 전체 시스템을 설계합니다.

---

## 📊 현재 상태 진단

| 항목 | 상태 | 설명 |
|------|------|------|
| 로봇 모델 (SDF) | ⚠️ 센서/구동 포함, 검증 필요 | RGB-D 카메라, LiDAR, IMU, DiffDrive가 정의되어 있고 Nav2용 토픽/프레임 정합성 점검이 필요 |
| 월드 환경 | ✅ 기본 완성 | 비닐하우스, 토마토, 잎사귀 모델 배치됨 |
| 커스텀 메시지/서비스 | ✅ 정의됨 | `CropStatus`, `EnvironmentData`, `IoTCommand`, `SetHumidity` |
| perception 패키지 | ⚠️ 데이터셋 유틸 존재 | 코드북, 데이터셋 감사/매니페스트 스크립트는 있으나 런타임 추론 노드는 없음 |
| navigation 패키지 | ❌ 골격만 존재 | 패키지 설정만 있고 Nav2/SLAM 설정 및 런치는 없음 |
| control 패키지 | ❌ 골격만 존재 | 미션 매니저, 수확 동작, 구역 제어 노드 없음 |
| iot 패키지 | ❌ 골격만 존재 | MQTT 브릿지, 환경 센서, 급수/커튼/환기/영양제 제어 노드 없음 |
| bringup 패키지 | ✅ 기본 완성 | 시뮬레이션 런치와 spawn/bridge 런치가 있으며 통합 런치는 추가 필요 |
| 백엔드 서버 | ❌ 없음 | 데이터 저장·API 없음 |
| 사용자 UI | ❌ 없음 | 대시보드·모바일 앱 없음 |

## 🤖 센서 및 구동계 현황

현재 `agribot_ws/src/agribot_description/models/agribot/model.sdf`에는 아래 센서와 구동계가 이미 정의되어 있습니다. 다음 단계는 "추가"보다 "토픽/프레임/성능 검증 및 Nav2 연계"입니다.

| 센서/구동 | 현재 상태 | 다음 작업 |
|------|-----------|-----------|
| **RGB-D 카메라** | 정의됨 | 이미지, depth, camera info 브리지 토픽 정합성 확인 |
| **2D LiDAR** | 정의됨 | `/scan` 브리지와 코스트맵 연동 확인 |
| **IMU** | 정의됨 | 오도메트리/자세 추정에 필요한 프레임 일치 여부 확인 |
| **Differential Drive** | 정의됨 | `cmd_vel`, `odom`, TF, 바퀴 파라미터 튜닝 |

## 🔄 핵심 데이터 흐름

### 병든 잎 감지 → 사용자 알림
```
카메라 이미지 → YOLOv8 추론 → 병해 판별 → ROS Topic 발행
      → IoT 브릿지 (MQTT) → 백엔드 서버 → 대시보드/모바일 푸시 알림
```

### 토마토 수확
```
카메라 이미지 → YOLOv8 추론 → 익은 토마토 감지 → 위치 추정
      → Nav2로 접근 → 수확 동작 (매니퓰레이터 or 시뮬레이션 이벤트)
      → 수확 기록 → 백엔드 DB 저장
```

### 자율 순찰
```
SLAM으로 지도 생성 → 순찰 경로 생성 (Waypoints)
      → Nav2로 경로 추종 → 카메라로 작물 모니터링
      → 물주기/영양제 필요 시 IoT 명령 발행
```

### 환경 이상 감지 → 주변 IoT 장치 제어
```
환경 센서(온도/습도/토양수분/조도) → 규칙 엔진
      → 급수 펌프 / 천장 커튼 / 환기팬 / 영양제 추천 판단
      → MQTT → IoT 제어 노드 → 실행 결과 저장 → 대시보드 반영
```

### 사용자 수동 제어 → IoT 장치 실행
```
대시보드 버튼 → 백엔드 API → MQTT → IoT 제어 노드
      → 장치 상태 변경 → 실행 성공/실패 저장 → 실시간 화면 갱신
```

## 🌐 이번 프로젝트에 반드시 들어가야 하는 IoT 상호작용

이 프로젝트에서 IoT는 "로봇이 상황을 보고, 주변 장치를 실제로 움직여서 환경을 바꾸는 기능"입니다.  
비전공자 기준으로 보면 아래처럼 생각하면 됩니다.

- 로봇: 보고 판단하는 역할
- 백엔드: 기록하고 중계하는 역할
- IoT 장치: 실제로 물을 주고, 커튼을 치고, 환기시키는 역할

### P0 필수 IoT 장치

| 장치 | 하는 일 | 언제 쓰는가 | 자동/수동 | 데모에서 꼭 보여줄 것 |
|------|---------|-------------|-----------|-----------------------|
| **급수 펌프/밸브** | 특정 구역에 물 공급 | 토양수분이 낮을 때 | 자동 + 수동 | 실행 후 기록이 남고 화면에 반영 |
| **천장 커튼 모터** | 햇빛과 내부 열 조절 | 온도/조도가 높을 때 닫기, 낮을 때 열기 | 자동 + 수동 | 열림 정도가 바뀌고 상태가 표시됨 |
| **환기팬** | 습도와 병해 위험 완화 | 습도가 높거나 곰팡이성 병해 위험이 클 때 | 자동 + 수동 | 팬 on/off와 실행 시간이 기록됨 |
| **영양제 장치** | 영양제 공급 | 규칙에 맞을 때 추천, 기본은 사용자 승인 후 실행 | 수동 중심 | 추천 이유와 실행 기록이 남음 |

### 구현할 때 꼭 지켜야 하는 원칙

- 실제 하드웨어가 없어도 괜찮습니다. Gazebo + 가상 제어 노드로 `상태 변화 + 로그 + 화면 반영`까지 연결되면 IoT 연동으로 인정할 수 있습니다.
- 중요한 것은 장치를 정말 움직이는 장면 자체보다, `명령 발행 → 장치 상태 변경 → 실행 결과 저장 → 대시보드 반영` 흐름이 끊기지 않는 것입니다.
- 영양제는 잘못 자동 실행하면 설명이 어려워질 수 있으므로, **추천은 자동 / 실행은 사용자 승인** 방식이 가장 안전합니다.

## 📦 패키지별 개발 계획

### 1단계: 로봇 하드웨어 (agribot_description)
> 이미 정의된 센서/구동계를 검증하고 Nav2/인지가 바로 사용할 수 있도록 정리합니다.

- `model.sdf`의 센서/바퀴/관성 파라미터 검증 및 보정
- `spawn_agribot.launch.py`의 `ros_gz_bridge` 토픽명, 프레임명, depth 브리지 검증
- Nav2와 perception이 바로 쓰는 공용 토픽 네이밍으로 정리

### 2단계: 자율주행 (agribot_navigation)
> 지도를 만들고, 그 위에서 자율주행합니다.

- SLAM Toolbox로 비닐하우스 지도 생성
- Nav2 설정 (경로 계획, 장애물 회피, 로컬/글로벌 코스트맵)
- Waypoint 순찰 노드 작성

### 3단계: AI 인식 (agribot_perception)
> 카메라로 작물 상태를 판단합니다.

- YOLOv8 모델 학습 (토마토 익음/안익음, 병든 잎사귀)
- ROS 2 인식 노드: 카메라 이미지 → 추론 → 결과 발행
- 병해 분류 결과를 `CropStatus` 메시지로 발행

### 4단계: 제어 및 동작 (agribot_control)
> 로봇의 물리적 동작을 제어합니다.

- `cmd_vel` 처리 (Differential Drive)
- 수확 동작 시퀀스 (시뮬레이션에서는 모델 제거/이동으로 대체)
- 물주기/커튼/환기/영양제 실행 판단 규칙
- 자동 제어와 사용자 수동 제어 우선순위 관리

### 5단계: IoT 통신 (agribot_iot)
> ROS 2 ↔ 외부 서비스 간 브릿지를 구현합니다.

- MQTT 클라이언트 노드 (ROS 2 토픽 → MQTT 브로커)
- 환경 데이터 수집 (가상 온도, 습도, 토양수분, 조도 센서)
- 급수 펌프, 천장 커튼, 환기팬, 영양제 장치 제어 노드
- IoT 명령 수신, 실행 결과 발행, 장치 상태 발행

### 6단계: 백엔드 서버 (신규 패키지 or 별도 프로젝트)
> 데이터를 저장하고 API를 제공합니다.

| 구성요소 | 기술 스택 | 역할 |
|----------|-----------|------|
| **API 서버** | FastAPI (Python) | REST API 제공 |
| **데이터베이스** | PostgreSQL | 작물 상태, 수확 기록, 환경 데이터 저장 |
| **메시지 브로커** | Mosquitto (MQTT) | ROS 2 ↔ 백엔드 실시간 통신 |
| **알림 서비스** | Firebase FCM or WebSocket | 사용자에게 실시간 알림 |

#### 주요 API 예시:
```
GET  /api/crops              → 전체 작물 상태 목록
GET  /api/crops/{id}/history → 특정 작물의 상태 이력
GET  /api/diseases           → 감지된 병해 목록
POST /api/harvest            → 수확 기록 저장
GET  /api/environment        → 환경 데이터 조회
POST /api/robot/command      → 로봇에게 명령 전달
POST /api/actuations/watering → 물주기 실행
POST /api/actuations/curtain  → 천장 커튼 제어
POST /api/actuations/fan      → 환기팬 제어
POST /api/actuations/nutrients → 영양제 실행
GET  /api/actuations/history  → 장치 실행 이력
GET  /api/iot/devices         → IoT 장치 상태 조회
```

### 7단계: 사용자 인터페이스 (신규 프로젝트)
> 사용자가 농장을 모니터링하고 제어합니다.

### 📅 1주차: 🤖 센서/구동 검증 및 브릿지 정합

> **이번 주 목표**: 이미 들어가 있는 센서와 바퀴가 ROS 2 기준으로 안정적으로 동작하도록 정리하고, 다음 주 Nav2/인지 작업이 바로 가능하게 만듭니다.

#### 🧠 이번 주에 알아야 할 핵심 개념
| 용어 | 쉬운 설명 |
|------|-----------|
| **SDF 파일** | 로봇의 설계도. XML 형식으로 생김새, 센서, 바퀴를 정의합니다 |
| **센서 플러그인** | Gazebo에서 카메라/라이다 등을 시뮬레이션해주는 부품 |
| **Differential Drive** | 양쪽 바퀴 속도를 다르게 해서 방향을 바꾸는 구동 방식 (로봇 청소기처럼) |
| **ros_gz_bridge** | Gazebo의 센서 데이터를 ROS 2로 넘겨주는 통역사 |
| **Topic** | ROS 2에서 데이터가 흐르는 파이프라인 (예: `/camera/image` → 카메라 이미지가 흐름) |

#### ✅ 구체적 작업 순서

**작업 1-1: 로봇 SDF 센서/프레임 검증**
- 파일: `agribot_ws/src/agribot_description/models/agribot/model.sdf`
- 확인할 항목:
  - **RGB-D 카메라**: 이미지, depth, camera info 토픽이 기대 이름으로 나오는지 확인
  - **2D LiDAR**: `/scan` 브리지 후 Nav2에서 바로 쓸 수 있는지 확인
  - **IMU**: frame id와 publish rate 확인
  - **바퀴/캐스터**: wheel radius, separation, collision, friction 재점검

**작업 1-2: Differential Drive/오도메트리 보정**
- `model.sdf` 안의 `gz-sim-diff-drive-system` 파라미터 검증
- `/cmd_vel`, `/odom`, `odom -> base_link` 변환이 안정적인지 확인
- 키보드 조종 시 직진 편차와 회전 응답 확인

**작업 1-3: ros_gz_bridge 설정**
- `spawn_agribot.launch.py`에 브릿지 노드 추가
- Gazebo 센서 데이터 → ROS 2 토픽으로 매핑:
  - 카메라 이미지 → `/agribot/camera/image`
  - LiDAR 스캔 → `/agribot/lidar/scan`
  - IMU 데이터 → `/agribot/imu`
  - 오도메트리 → `/odom`

**작업 1-4: 빌드 및 테스트**
```bash
# 빌드
cd ~/SSAFY/S14P21A602/agribot_ws
```

### 📅 4주차: 🔗 인식 + 자율주행 + IoT 연동

> **이번 주 목표**: 로봇이 토마토와 병든 잎을 본 뒤 행동으로 이어지고, 환경값에 따라 주변 IoT 장치까지 움직이게 만듭니다.

#### 🧠 이번 주에 알아야 할 핵심 개념
| 용어 | 쉬운 설명 |
|------|-----------|
| **Behavior Tree (BT)** | 로봇의 의사결정 로직을 나무 구조로 표현 ("만약 토마토 발견 → 다가감 → 수확") |
| **MQTT** | IoT 기기들이 메시지를 주고받는 경량 프로토콜 (카카오톡 같은 것) |
| **브로커** | MQTT 메시지를 중계해주는 서버 (우체국 같은 역할) |
| **Action** | ROS 2에서 "시간이 오래 걸리는 작업"을 요청하고 진행상황을 확인하는 방식 |
| **수동 우선 제어** | 자동으로 움직이더라도 사용자가 강제로 멈추거나 직접 실행할 수 있게 하는 원칙 |

#### ✅ 구체적 작업 순서

**작업 4-1: 미션 매니저 노드 작성**
- `agribot_control/agribot_control/mission_manager.py` 작성
- 행동 로직:
  1. 순찰 중 → AI가 익은 토마토 감지 → Nav2에 "토마토 위치로 이동" 요청
  2. 토마토에 도착 → 수확 동작 (시뮬레이션에서는 토마토 모델 제거)
  3. 병든 잎 감지 → 알림 토픽 발행 + MQTT로 외부 전송
  4. 환경값 확인 → 급수/커튼/환기/영양제 추천 규칙 확인
  5. 자동 실행 가능 항목은 IoT 명령 발행, 위험한 항목은 사용자 승인 대기

**작업 4-2: MQTT 브릿지 구축**

- `agribot_iot/agribot_iot/mqtt_bridge_node.py` 작성
- 하는 일:
  - ROS 2 토픽 → MQTT 메시지로 변환하여 외부 전송
  - 예: `/disease_alert` → MQTT `agribot/alerts/disease`
  - 예: `/crop_status` → MQTT `agribot/crops/status`
  - 예: `/iot/device_state` → MQTT `agribot/iot/device_state`

**작업 4-3: 가상 환경 센서 노드**

- 이 데이터도 MQTT를 통해 백엔드로 전송

**작업 4-4: 주변 IoT 장치 제어 노드 작성**
- `agribot_iot/agribot_iot/watering_controller_node.py` 작성
  - 구역별 물주기 시작/정지, 실행 시간, 공급량 기록
- `agribot_iot/agribot_iot/curtain_controller_node.py` 작성
  - 천장 커튼 열기/닫기/열림 비율 변경 처리
- `agribot_iot/agribot_iot/fan_controller_node.py` 작성
  - 환기팬 on/off, 속도 단계 처리
- `agribot_iot/agribot_iot/nutrient_controller_node.py` 작성
  - 영양제 장치 실행 요청과 실행 결과 기록

**작업 4-5: 자동 제어 규칙 정리**
- 토양수분이 낮으면 급수 후보로 올리기

## 💡 백엔드가 필요한 이유

> **Q: 로봇이 이런 기능을 하려면 백엔드가 필요한가?**
> **A: ✅ 네, 반드시 필요합니다.**

| 기능 | 왜 백엔드가 필요한가? |
|------|----------------------|
| 병든 잎 알림 | 로봇(ROS 2)이 발견한 병해 정보를 **사용자 앱/웹에 전달**하려면 중간 서버 필요 |
| 물주기 이력 | 언제 물을 줬는지 **기록을 저장**할 DB 필요 |
| 천장 커튼 제어 | 사용자가 웹에서 열고 닫거나 자동 실행 결과를 공유하려면 중간 서버 필요 |
| 환기팬 제어 | 환경값 기준 자동 실행과 수동 실행을 같은 기준으로 관리하려면 서버 필요 |
| 영양제 권장량 | 병해 + 작물 상태를 분석하여 **추천 로직** 실행할 서버 필요 |
| 수확 통계 | 수확 기록을 **누적 저장**하고 통계를 보여줄 서버 필요 |
| 사용자 제어 | 사용자가 웹/앱에서 로봇에 **명령을 보내려면** 중계 서버 필요 |

### ROS 2 ↔ 백엔드 ↔ UI 전체 흐름

```
ROS 2 (로봇 내부)                   백엔드 (서버)               UI (사용자)
┌─────────────┐    MQTT/HTTP    ┌──────────────┐   REST/WS   ┌──────────┐
│ 센서 데이터   │ ──────────────→ │ API 서버     │ ──────────→ │ 대시보드  │
│ AI 추론 결과  │ ──────────────→ │ + DB 저장    │ ──────────→ │ 모바일앱  │
│ 로봇 상태    │ ──────────────→ │ + 알림 전송   │            │          │
│ 수확/IoT 제어 │ ──────────────→ │              │            │          │
│              │ ←────────────── │ 사용자 명령   │ ←────────── │ 명령 입력 │
└─────────────┘                 └──────────────┘            └──────────┘
```

### P0 필수 데모 시나리오

1. 로봇이 정적 지도에서 자기 위치를 잡고 순찰을 시작한다.
2. 구역 waypoint를 따라 이동하며 카메라로 잎사귀/토마토를 관찰한다.
3. 병든 잎을 감지하면 알림과 스냅샷을 백엔드로 전달한다.
4. 익은 토마토를 감지하면 접근 위치로 이동하고 수확 시퀀스를 실행한다.
5. 수확 성공 후 토마토 모델을 바구니로 적재 처리하고 이력을 저장한다.
6. 수확이 끝나면 로봇이 최초 순찰 시작 위치 또는 지정한 `home_pose`로 복귀한다.
7. 환경 데이터와 질병/성장 상태를 조합해 급수, 천장 커튼, 환기팬을 자동 제어하거나 실행 후보로 올린다.
8. 영양제는 추천 이유를 화면에 보여 주고 사용자가 승인하면 실행한다.
9. 대시보드에서 로봇 상태, 지도, 알림, 수확, IoT 장치 상태와 실행 이력을 실시간 확인한다.

## 🧭 Nav2 자율주행 구현 상세 전략

비닐하우스는 구조가 반복적이고 장애물이 대부분 고정되어 있으므로, 최종 시연 기준으로는 `지도 작성 단계`와 `운용 단계`를 분리하는 것이 가장 안정적입니다.

### 1. 지도 작성 단계

- `slam_toolbox`로 한 번만 지도를 생성합니다.
- 키보드 조종 또는 단순 patrol 스크립트로 모든 통로를 1회 이상 지나갑니다.
- 결과물을 `agribot_navigation/maps/greenhouse_map.yaml`, `greenhouse_map.pgm`로 Git에 커밋합니다.
- 이후 데모에서는 SLAM을 끄고 정적 지도 기반 `AMCL`을 사용합니다.

### 2. 정적 지도 기반 운용 단계

필수 노드 구성:

- `map_server`
- `amcl`
- `planner_server`
- `controller_server`
- `bt_navigator`
- `behavior_server`
- `waypoint_follower`
- `lifecycle_manager`

추천 Nav2 조합:

| 항목 | 권장 선택 | 이유 |
|------|-----------|------|
| Global Planner | `SmacPlanner2D` | 격자 지도 기반 통로 주행에 안정적 |
| Local Controller | `RegulatedPurePursuit` | 차동구동 로봇에서 튜닝 난도가 낮고 좁은 통로 추종이 쉬움 |
| Localization | `AMCL` | 정적 온실 지도에서 반복 시연 안정성이 높음 |
| Recovery | `spin`, `back_up`, `wait` | 행 사이에서 막혔을 때 재시도 로직 단순화 가능 |

권장 초기 파라미터:

| 항목 | 권장 시작값 |
|------|-------------|
| costmap resolution | `0.05` |
| local costmap size | `4.0m x 4.0m` |
| inflation radius | `0.30 ~ 0.40m` |
| max linear velocity | `0.25 ~ 0.35m/s` |
| max angular velocity | `0.6 ~ 1.0rad/s` |
| goal tolerance | `0.15m`, `0.15rad` |

### 3. 순찰과 작물 접근을 분리한다

Nav2는 "가는 것"을 맡기고, "어떤 구역을 언제 갈지"는 상위 노드가 맡는 구조가 가장 깔끔합니다.

- `mission_manager`가 다음 순찰 구역을 선택
- `patrol_node`가 행 단위 waypoint를 순서대로 요청
- 작물이 감지되면 `approach pose`를 별도로 계산하여 `NavigateToPose` 재요청
- 접근 후에는 속도를 낮추고 정면 정렬만 수행
- 수확/촬영이 끝나면 원래 patrol 큐로 복귀

### 4. 비닐하우스 waypoint 설계 원칙

- 식물마다 목표점을 찍지 말고 `행(row)`과 `구역(zone)` 기준으로 waypoint를 설계합니다.
- 각 행마다 `entry`, `inspect`, `turn`, `exit` waypoint 4종만 두고, 식물은 행 내부 관측 대상으로 관리합니다.
- 작물 접근은 "현재 행의 inspect point"에서 세부 접근점으로만 짧게 파생시킵니다.
- 이 구조가 지도 수정, 식물 추가, 티켓 분할에 가장 강합니다.

### 2. 클래스 설계는 과하지 않게 시작한다

초기 권장 클래스:

| 클래스 | 용도 |

설명:

- 처음부터 모든 병명을 다 넣으면 데이터 불균형으로 성능이 흔들립니다.
- 최소 3종 질병 + 정상 잎 + 익은/안 익은 토마토 정도로 시작하는 것이 가장 현실적입니다.
- 영양제 추천은 `질병 클래스 + 토양 수분 + 습도 + 성장 단계`를 함께 보아야 합니다.

### 3. 추론 파이프라인

`detector_node.py`의 역할:

1. `/agribot/camera/image` 구독
2. `/agribot/camera/depth_image`, `/agribot/camera/camera_info` 동기화
3. YOLO 추론을 CUDA로 실행
4. 바운딩 박스 중심 또는 박스 내부 median depth로 3D 좌표 추정
5. 카메라 좌표를 `base_link`, `map` 기준으로 변환
6. 질병/토마토 관측 결과를 구조화 메시지로 발행
7. 주석 이미지와 스냅샷을 저장 또는 스트리밍

### 4. 건강 점수와 추천 규칙

건강 점수는 모델 confidence를 그대로 쓰지 말고 규칙으로 정규화합니다.

예시:

- `healthy_leaf`만 관측: `health_score = 0.9 ~ 1.0`
- 경증 질병 1회 관측: `health_score = 0.6 ~ 0.8`
- 중복 질병 또는 낮은 토양 수분 동반: `health_score = 0.3 ~ 0.5`
- 2회 연속 이상 관측: 알림 우선순위 상승

환경 제어 추천 규칙:

- `soil_moisture < threshold`이면 급수 우선
- `temperature`와 `illuminance`가 동시에 높으면 천장 커튼 일부 닫기
- `humidity`가 높고 곰팡이 계열이 반복되면 환기 또는 급수 보류
- 질병 코드와 성장 단계가 특정 조합일 때만 영양제 추천
- 즉, "잎사귀 사진만 보고 영양제 양을 바로 결정"하지 않습니다.

### 5. RTX 4070 laptop GPU 활용 기준

- 학습은 `yolov8n`으로 빠르게 baseline을 만들고, 여유가 있으면 `yolov8s`까지 비교합니다.
- 추론은 FP16을 우선 적용합니다.
- 실험 결과는 `runs/` 전체를 Git에 올리지 말고, `best.pt`, `args.yaml`, 성능 표만 정리해 커밋합니다.
- 모델 파일이 크면 Git LFS 또는 사내 공유 스토리지 중 한 가지 방법으로 팀 전체에 동일 버전을 배포합니다.

## 🦾 토마토 수확 및 바구니 적재 구현 전략

현재 저장소에는 매니퓰레이터가 없으므로 수확 구현은 반드시 단계적으로 나눠야 합니다.

### 1. P0 완주형 구현

P0에서는 "자율주행 + 시각 인지 + 수확 이벤트 + 바구니 적재"를 완주하는 것이 목표입니다.

구현 방식:

- 로봇 본체에 간단한 3~4자유도 암 또는 preset animation용 링크를 추가
- 토마토 검출 후 `pre-grasp pose`까지 Nav2로 접근
- 짧은 정렬 동작 후 수확 액션 실행
- 수확 성공 조건은 `엔드이펙터와 목표 토마토 간 거리 임계값`으로 판정
- 성공 시 Gazebo 서비스 또는 커스텀 노드로 토마토 모델을 월드에서 제거
- 바구니 위치에 토마토 모델을 다시 생성하거나 바구니 카운트만 증가

### 2. P1 고도화 구현

- 실제 관절형 로봇팔 모델링
- 그리퍼 개폐
- MoveIt2 기반 IK/경로 계획
- 토마토와 잎사귀 충돌 회피

### 3. 수확 시퀀스 권장 상태 머신

`SEARCH -> APPROACH -> ALIGN -> PICK -> VERIFY -> PLACE -> RETURN_HOME -> RESUME`

각 상태의 역할:

- `SEARCH`: perception에서 수확 가능한 토마토를 대기
- `APPROACH`: Nav2로 사전 접근 위치 이동
- `ALIGN`: 로컬 속도를 낮추고 정면 오차 보정
- `PICK`: 암/그리퍼 또는 시뮬레이션 수확 액션 실행
- `VERIFY`: 수확 성공, 실패, 재시도 여부 판단
- `PLACE`: 바구니 적재 처리
- `RETURN_HOME`: 최초 순찰 시작 위치 또는 지정한 home pose로 복귀
- `RESUME`: 다음 순찰 구역 복귀

### 4. 수확 구현에서 절대 놓치면 안 되는 것

- 토마토마다 `fruit_id`, `plant_id`, `zone_id`를 부여합니다.
- perception 결과와 world 메타데이터를 매칭할 수 있어야 합니다.
- 수확 실패도 이벤트로 저장해야 합니다.
- 바구니 적재 수량은 백엔드 `harvest_events`에 누적합니다.

### 3. ROS 2와 백엔드의 실시간 연동

권장 흐름:

1. ROS 2 노드가 MQTT로 관측/상태/이벤트 발행

3. 백엔드가 WebSocket으로 프론트엔드에 실시간 전파
4. 프론트엔드 명령은 REST로 생성
5. 백엔드가 명령을 MQTT로 ROS 2에 전달
6. ROS 2가 결과를 다시 MQTT로 반환

## 🧱 처음부터 끝까지 완성하는 실행 순서

이 절은 "어떤 순서로 티켓을 닫아야 프로젝트가 완성되는지"를 초보자 기준으로 설명합니다. 아래 순서를 지키면 중간에 길을 잃지 않습니다.

4. **IoT 규칙 완성**: 급수, 천장 커튼, 환기팬, 영양제 추천 기준과 수동 우선 규칙을 고정합니다.
5. **장치 제어 완성**: 급수/커튼/환기/영양제 장치 노드가 실제로 상태를 바꾸고 결과를 돌려주게 합니다.
6. **수확 완성**: 로봇팔 또는 시뮬레이션 수확 시퀀스로 토마토를 따고 바구니에 담고 home 위치로 복귀시킵니다.
7. **백엔드 완성**: MQTT, DB, API, WebSocket을 붙여 로봇 이벤트와 IoT 장치 이력이 모두 저장되고 조회되게 합니다.
8. **프론트엔드 완성**: 병든 잎 감지, IoT 제어, 수확 이력, 로봇 상태를 화면에 표시합니다.
9. **통합 리허설**: 새로 pull 받은 팀원도 같은 결과를 재현하도록 테스트와 문서를 잠급니다.

## 🎫 세분화된 지라 백로그 가이드

이슈 키는 예시로 `S14P-###`를 사용합니다. 실제 Jira 프로젝트 키에 맞게 번호만 치환해서 사용하면 됩니다.

### 읽는 법

- `쉬운 설명`: 비전공자 기준으로 이 티켓이 왜 필요한지 설명합니다.
- `해야 할 일`: 이 티켓에서 팀원이 실제로 무엇을 확인하고, 만들고, 정리하면 되는지 쉬운 문장으로 적었습니다.
- `결과물`: 이 티켓을 닫을 때 남아야 하는 파일, 설정, 화면, 로그입니다.
- `확인 방법`: 누가 봐도 끝났다고 판단할 수 있는 검증 기준입니다.
- `선행`: 먼저 끝나 있어야 하는 티켓입니다.

### Epic A. Simulation / World / Bringup

`S14P-101` 센서 출력 점검
- 쉬운 설명: 로봇이 지금 어떤 센서 데이터를 내보내는지 먼저 확인하는 티켓
- 해야 할 일: 카메라, 거리 센서(LiDAR), IMU, 위치값(`/odom`)이 실제로 잘 나오는지 하나씩 확인하고, 각 데이터의 이름, 데이터 종류, 나오는 속도를 표로 정리
- 결과물: 센서 점검표, bridge 수정 포인트 목록
- 확인 방법: `ros2 topic list`, `ros2 topic hz`, `ros2 topic echo --once`로 핵심 토픽이 모두 보임
- 선행: 없음

`S14P-102` 로봇 부품 좌표 정합
- 쉬운 설명: 로봇이 "내 몸통", "카메라", "라이다"가 서로 어디에 있는지 올바르게 알아야 하는 티켓
- 해야 할 일: 로봇 몸체, 카메라, 라이다, IMU, 지도 기준점이 서로 어떤 위치 관계인지 확인하고, 이름이 틀리거나 빠진 부분이 있으면 고치기
- 결과물: 프레임 구조 정리 내용, 필요한 launch 또는 SDF 수정
- 확인 방법: `tf2_tools` 또는 RViz2에서 프레임 트리가 정상 표시됨
- 선행: `S14P-101`

`S14P-103` 주행·오도메트리 보정
- 쉬운 설명: 로봇이 앞으로 가라고 했을 때 똑바로 가고, 위치가 틀어지지 않도록 맞추는 티켓
- 해야 할 일: 바퀴 크기, 바퀴 사이 거리, 위치값 갱신 속도, 직진할 때 한쪽으로 쏠리는지, 회전이 너무 빠르거나 느린지 확인하고 값 조정
- 결과물: 보정된 `model.sdf` 또는 설정값
- 확인 방법: teleop로 직진 3회 테스트 시 큰 편차 없이 이동하고 `/odom`이 정상 증가함
- 선행: `S14P-102`

`S14P-104` 비닐하우스 구역 정의
- 쉬운 설명: 비닐하우스를 "1구역, 2구역"처럼 나눠서 이후 급수와 알림을 연결하는 티켓
- 해야 할 일: 비닐하우스를 몇 개 구역으로 나눌지 정하고, 각 구역의 이름(`zone_id`), 범위, 대표 위치를 파일로 정리
- 결과물: `zones.yaml` 또는 동등한 메타데이터 파일
- 확인 방법: 팀원들이 같은 `zone_id`를 보고 같은 위치를 말할 수 있음
- 선행: `S14P-101`

`S14P-105` 식물·토마토 ID 정의
- 쉬운 설명: 어떤 식물에서 어떤 토마토를 발견했는지 추적하려면 고유 번호가 필요한 티켓

- 결과물: `plants.yaml`, `fruits.yaml` 또는 동등한 파일

- 선행: `S14P-104`

`S14P-106` 통합 실행 설정 표준화
- 쉬운 설명: 팀원이 누구든 같은 명령으로 시스템을 켤 수 있게 만드는 티켓
- 해야 할 일: 시뮬레이션 실행 파일, 전체 실행 파일, 환경 변수 예시, GPU 사용 방법, 실행 순서를 문서로 정리해서 누구나 같은 순서로 시작할 수 있게 만들기

## 🗂️ 문서 역할 분리 기준

팀 협업에서는 "모든 내용을 한 문서에 다 적는 것"보다
"어떤 문서가 어떤 수준의 정보를 책임지는지"를 먼저 고정하는 것이 더 중요합니다.

이 프로젝트에서는 아래 기준으로 문서를 나눕니다.

### 1. 어떤 내용이 가이드 문서에 포함되어 있는가

현재 이 문서에는 아래 수준의 내용이 포함됩니다.

- 프로젝트 목표와 범위
- 시스템 아키텍처
- 주차별 개발 계획
- 핵심 데이터 흐름
- 이벤트 중심 DB 테이블 목록
- 필수 백엔드 API 목록
- MQTT 토픽 계약
- 협업 규칙, 역할 분담, 통합 체크리스트

즉, 이 문서는 팀 전체가 "무엇을 왜 만들고, 어떤 순서로 완성할지"를 맞추는 상위 안내서입니다.

### 2. 어떤 내용은 별도 문서의 원본으로 관리하는가

아래 문서들은 가이드 문서의 하위 상세 설계 문서로 봅니다.

| 문서 | 역할 | 이 문서에 있어야 하는 수준 |
|------|------|------------------------------|
| `수확해조_프로젝트_개발_계획_및_협업_가이드.md` | 프로젝트 전체 방향과 협업 기준 | 요약, 범위, 필수 목록, 선행 관계, 운영 규칙 |
| `ERD_구조_예시.md` | 데이터 구조 설명의 원본 | 테이블 관계, 컬럼 의미, boolean/enum 설명, 왜 필요한지 |
| `API_명세서.md` | API 계약의 원본 | 엔드포인트, 요청/응답 예시, 쿼리 파라미터, WebSocket 이벤트 |
| `DB_SCHEMA_초안.sql` | DB 구현 초안의 원본 | `CREATE TABLE`, `ENUM`, `FK`, `INDEX`, `CHECK` |

### 3. 문서별 단일 진실 원천(Source of Truth)

문서가 여러 개일 때 가장 중요한 것은 "어느 문서를 최종 기준으로 볼 것인가"를 정하는 것입니다.

이 프로젝트에서는 아래처럼 정합니다.

- 프로젝트 범위, 일정, 우선순위, 팀 협업 규칙:
  - **기준 문서 = `수확해조_프로젝트_개발_계획_및_협업_가이드.md`**
- 데이터 모델 구조와 컬럼 의미:
  - **기준 문서 = `ERD_구조_예시.md`**
- 백엔드 엔드포인트 계약:
  - **기준 문서 = `API_명세서.md`**
- 실제 PostgreSQL 초기 스키마 초안:
  - **기준 문서 = `DB_SCHEMA_초안.sql`**

즉, 가이드 문서에 요약이 들어 있더라도
컬럼 단위 설명이나 요청/응답 payload처럼 구현 세부사항은 별도 문서를 우선 기준으로 봅니다.

### 4. 무엇을 가이드 문서에 남기고, 무엇을 빼는가

#### 가이드 문서에 남기는 것

- "반드시 있어야 하는 테이블/엔드포인트" 목록
- 데이터 흐름과 시스템 연결 구조
- API/DB/IoT가 왜 필요한지에 대한 설명
- 주차별 구현 목표와 팀원 간 선행 관계

#### 가이드 문서에서 빼고 별도 문서로 넘기는 것

- 각 테이블의 모든 컬럼 정의
- boolean, enum, 상태값의 세부 의미
- 요청/응답 JSON 예시
- SQL 제약조건, 인덱스, 트리거
- 세부적인 예외 처리 규칙

이유는 간단합니다.

- 가이드 문서까지 너무 상세해지면 읽는 사람이 전체 흐름을 놓칩니다.
- 반대로 상세 설계 문서가 없으면 구현 단계에서 팀원마다 다른 해석이 생깁니다.

### 5. 현재 문서 기준으로 포함 여부를 어떻게 판단할까

예를 들어 아래처럼 판단합니다.

- `iot_devices`, `actuation_commands`, `actuation_logs` 같은 핵심 테이블 이름이 가이드에 있으면:
  - **개념은 포함된 것**
- `actuation_recommendations`처럼 추천/승인 흐름을 위한 세부 테이블 구조가 ERD에만 있으면:
  - **상세 설계는 별도 문서에 있는 것**
- `/api/v1/actuations/watering` 같은 엔드포인트 이름이 가이드에 있으면:
  - **필수 API 범위는 포함된 것**
- 요청 body 예시, 응답 body 예시, 상태값 정의가 API 문서에만 있으면:
  - **구현 계약은 별도 문서가 기준**

즉, "가이드에 이름이 있다"와 "구현 가능한 수준으로 정의돼 있다"는 다릅니다.

### 6. 문서 동기화 규칙

아래 변경이 생기면 관련 문서를 반드시 함께 수정합니다.

| 변경 종류 | 반드시 함께 수정할 문서 |
|-----------|--------------------------|
| 테이블 추가/삭제 | `ERD_구조_예시.md`, `DB_SCHEMA_초안.sql`, 필요 시 가이드 요약표 |
| 컬럼 추가/삭제 | `ERD_구조_예시.md`, `DB_SCHEMA_초안.sql` |
| API 추가/삭제 | `API_명세서.md`, 필요 시 가이드 API 목록 |
| IoT 추천/승인 흐름 변경 | `ERD_구조_예시.md`, `API_명세서.md`, 가이드 IoT 설명 |
| MQTT 토픽 변경 | 가이드 문서, MQTT 규약 문서, 관련 구현 코드 |

### 7. MR에서 꼭 확인할 문서 체크

Merge Request를 올릴 때 아래 질문에 "예"가 되어야 합니다.

- 이번 변경으로 테이블 구조가 달라졌는가?
- 이번 변경으로 API 요청/응답이 달라졌는가?
- 이번 변경으로 IoT 장치 상태/추천/명령 흐름이 달라졌는가?
- 이번 변경으로 팀원이 pull 받아 실행할 때 필요한 문서가 달라졌는가?

하나라도 "예"면 관련 문서를 같은 MR에서 같이 수정합니다.

### 8. 현재 프로젝트에서 문서를 이렇게 읽으면 된다

초보자 기준 추천 읽기 순서는 아래와 같습니다.

1. `수확해조_프로젝트_개발_계획_및_협업_가이드.md`
2. `ERD_구조_예시.md`
3. `API_명세서.md`
4. `DB_SCHEMA_초안.sql`

읽는 목적도 다릅니다.

- 가이드 문서:
  - 전체 흐름 이해
- ERD 문서:
  - 어떤 데이터를 왜 저장하는지 이해
- API 문서:
  - 화면과 서버가 어떻게 대화하는지 이해
- DB 스키마:
  - 실제 구현에 필요한 SQL 구조 확인

### 9. 결론

이 문서에 API와 ERD 내용이 "부분적으로 포함"되어 있는 것은 맞습니다.
하지만 구현 기준으로 바로 쓰는 상세 내용은 별도 문서가 원본입니다.

따라서 협업 기준은 아래 한 줄로 정리합니다.

- **가이드는 방향과 범위의 기준**
- **ERD/API/SQL 문서는 구현 계약의 기준**

- `requirements.txt`, `package-lock.json` 또는 lock 파일을 유지
- `.env.example`을 제공하고 로컬 `.env` 값만 분리
- 절대 개인 PC 경로를 코드에 하드코딩하지 않음
- 시뮬레이터와 백엔드 실행 명령을 문서에 고정

## ✅ 최종 통합 검증 체크리스트

아래 체크리스트를 모두 통과하면 "프로젝트 완성"으로 판단합니다.

- `ros2 launch agribot_bringup full_system.launch.py` 한 번으로 전체 ROS 시스템이 뜬다.
- `docker compose up -d` 후 backend와 DB, MQTT가 동시에 정상 기동한다.
- 프론트엔드에서 현재 로봇 위치와 미션 상태를 실시간으로 본다.
- 로봇이 최소 1개 행을 자동 순찰한다.
- 병든 잎 감지 알림이 백엔드 DB와 프론트엔드에 반영된다.
- 익은 토마토 1개 이상을 수확하고 바구니 적재 수량이 증가한다.
- 수확 후 로봇이 최초 순찰 시작 위치 또는 `home_pose`로 복귀한다.
- 급수 명령 1회 이상이 발행되고 로그가 남는다.
- 천장 커튼 제어 1회 이상이 실행되고 열림 상태가 화면에 반영된다.
- 환기팬 제어 1회 이상이 실행되고 실행 시간이 기록된다.
- 영양제 추천이 화면에 표시되고 승인 후 실행 기록이 남는다.
- IoT 장치 실행 이력이 프론트엔드 화면에서 조회된다.
- 긴급 정지 버튼이 실제로 로봇 동작을 멈춘다.
- 팀원 2명 이상이 새로 pull 받은 환경에서 같은 시나리오를 재현한다.
