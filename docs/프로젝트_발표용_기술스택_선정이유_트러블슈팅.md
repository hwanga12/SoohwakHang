# 프로젝트 발표용 기술 스택, 선정 이유, 트러블슈팅 정리

## 1. 문서 목적

이 문서는 현재 `S14P21A602` 프로젝트를 발표할 때 바로 사용할 수 있도록 아래 내용을 한 번에 정리한 문서다.

- 현재 프로젝트의 실제 기술 스택
- 각 기술과 버전을 선택한 이유
- 지금까지 진행한 핵심 트러블슈팅 요약
- 발표 때 강조하면 좋은 시스템 구조 포인트

---

## 2. 프로젝트 한 줄 소개

`AgriBot`은 **Gazebo Harmonic + ROS 2 Jazzy** 기반의 스마트 농장 자율주행 로봇 시뮬레이션 프로젝트다.  
비닐하우스 환경에서 로봇이 주행하고, 작물을 인식하고, IoT 장치를 제어하며, 그 결과를 **백엔드 + 웹 대시보드**로 연결하는 것이 핵심 목표다.

---

## 3. 전체 시스템 구조

```text
Gazebo Harmonic
  -> 로봇, 센서, 온실 환경 시뮬레이션

ROS 2 Jazzy
  -> 주행, 위치추정, 센서 처리, 미션 제어, IoT 제어

MQTT / REST / WebSocket
  -> ROS 2 <-> 외부 서비스 계층 <-> 프론트엔드 연동

Backend (FastAPI + PostgreSQL)
  -> 데이터 저장, API 제공, 추론 확인, 웹소켓 송신

Frontend (React + Vite + TypeScript)
  -> 관제 대시보드, 맵, 상태 모니터링, 수동 제어
```

발표용 핵심 메시지는 아래처럼 잡으면 된다.

- `시뮬레이터`, `로봇 미들웨어`, `실시간 메시징`, `백엔드`, `관제 UI`까지 전체 파이프라인을 연결했다.
- 단순히 로봇만 움직이는 것이 아니라, **주행 -> 인식 -> 이벤트 -> 저장 -> 화면 반영** 흐름을 끝까지 만들었다.

## 5. 왜 현재 버전을 선택했는가

이 섹션은 “무조건 최신이라서”가 아니라, **현재 프로젝트 구조와 데모 안정성에 맞는 조합을 고른 이유**를 설명하는 용도다.

### 5.1 Ubuntu 24.04를 사용한 이유

- 이 저장소의 기본 실행 가이드가 `Ubuntu 24.04`를 기준으로 작성되어 있다.
- 프로젝트 루트 README와 센서 점검 문서가 모두 `Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic` 조합을 전제로 한다.
- 팀 기준 환경을 하나로 맞춰야 ROS 패키지, Gazebo plugin, GPU 설정, `rosdep` 설치 결과가 흔들리지 않는다.
- 발표 관점에서도 “운영 OS가 무엇인지”를 명확히 고정하는 것이 재현성 측면에서 유리하다.

### 5.2 ROS 2 Jazzy를 사용한 이유

- 현재 저장소의 설치 명령이 전부 `ros-jazzy-*` 패키지 기준으로 작성되어 있다.
- `agribot_bringup`, `agribot_navigation`, `agribot_description` 런치 파일과 설정이 모두 Jazzy 환경을 기준으로 정리돼 있다.
- ROS 2는 토픽, 서비스, 액션, TF, 런치, 패키지 구조를 한 번에 제공하므로 로봇 프로젝트 통합에 적합하다.
- 특히 우리 프로젝트처럼 **주행 + 인식 + IoT + UI 연동**을 동시에 다룰 때, 개별 스크립트보다 ROS 2가 구조적으로 훨씬 유리하다.

### 5.3 Gazebo Harmonic을 사용한 이유

- 루트 README에서 이미 `Gazebo Harmonic`을 기본 시뮬레이터로 명시하고 있다.
- `ros_gz_sim`, `ros_gz_bridge`, `ros_gz_image`를 통해 Gazebo 센서/월드와 ROS 2 토픽을 직접 연결할 수 있다.
- 실제 하드웨어 없이도 로봇, 카메라, LiDAR, 온실 구조물, 급수 효과까지 시뮬레이션할 수 있다.
- 발표 시 “실물 로봇 없이도 전체 서비스 흐름을 검증했다”는 점을 보여주기 좋다.

### 5.4 Nav2를 사용한 이유

- ROS 2 자율주행 표준 스택이라서 planner, controller, recovery, AMCL, map server를 일관된 구조로 구성할 수 있다.
- 우리 프로젝트는 직접 경로 계획기를 새로 만드는 것보다, **농장 환경에 맞는 파라미터 튜닝과 waypoint 설계**가 더 중요했다.
- 실제 문서상에서도 `SmacPlanner2D`, `RegulatedPurePursuitController`, `AMCL`, `behavior_server` 등을 조합해서 사용하고 있다.

### 5.5 YOLOv8을 사용한 이유

- 토마토와 병해처럼 시각적으로 구분 가능한 대상을 빠르게 탐지하기에 적합하다.
- Python 기반이라 ROS 노드와 백엔드에 모두 연결하기 쉽다.
- 현재 구조는 로봇에서 1차 추론을 수행하고, 백엔드에서 재확인하는 방식이라 **속도와 정확도 사이의 균형**을 잡기 좋다.

### 5.6 FastAPI를 사용한 이유

- 백엔드와 AI 로직이 Python 기반이어서 ROS/YOLO와 언어를 맞추기 쉽다.
- 라우터 기반으로 API를 빠르게 나눌 수 있고, 문서화도 쉽다.
- WebSocket을 같은 서버에서 같이 다루기 쉬워서 대시보드 실시간 반영에 적합하다.
- 발표 시 Swagger(`/docs`) 기반 API 문서화를 보여주기 좋다.

### 5.7 PostgreSQL을 사용한 이유

- 미션, 작물, 알림, 환경 데이터, 제어 이력처럼 **관계형 데이터**가 많다.
- SQLAlchemy 모델에서 UUID, JSONB 같은 구조를 사용하고 있어 도메인 확장성도 좋다.
- “현재 상태 조회 + 이력 관리 + 통계”를 같이 처리하기에 안정적이다.

### 5.8 Mosquitto(MQTT)를 사용한 이유

- ROS 2와 외부 서비스 계층을 느슨하게 연결하기에 적합하다.
- IoT 장치 제어나 상태 이벤트처럼 **짧고 빈번한 메시지**를 전달하는 데 유리하다.
- 코드상 MQTT 브리지가 broker 연결 실패 시 `log-only` fallback도 지원해 데모 안정성 확보에 도움이 된다.
- 발표에서는 “로봇 내부 이벤트를 웹 서비스 계층으로 넘기는 경량 메시지 브로커”라고 설명하면 된다.

### 5.9 Docker를 사용한 이유

- PostgreSQL, Mosquitto, pgAdmin을 팀원마다 동일하게 띄울 수 있다.
- 백엔드 인프라 의존성을 OS 전역 설치에 묶지 않고 분리할 수 있다.
- 발표에서는 “개발 환경 재현성과 서비스 의존성 표준화” 포인트로 설명하면 된다.

### 5.10 React + Vite + TypeScript를 사용한 이유

- 관제 대시보드는 반복 수정이 많기 때문에 개발 서버가 빠른 조합이 필요했다.
- TypeScript를 써야 API 응답 타입과 화면 상태가 꼬일 가능성을 줄일 수 있다.
- TanStack Query를 이용해 REST 데이터와 새로고침 흐름을 안정적으로 관리할 수 있다.
- WebSocket과 함께 쓰기 좋아서 실시간 관제 화면에 적합하다.

## 6. 핵심 트러블슈팅 요약

아래 내용은 실제 `docs/README.md`, `S14P-31`, `S14P-32`, `S14P-33`, `S14P-38`, `S14P-39` 등에 남아 있는 내용을 발표용으로 압축한 것이다.

### 6.1 Gazebo가 멈춘 상태로 시작해서 센서 토픽 이름만 있고 메시지가 안 나오던 문제

- 증상:
  - 토픽 목록은 보이는데 실제 `echo --once`가 안 됨
  - 카메라/센서 데이터가 안 흘러서 이후 인식과 주행 검증이 불가능
- 원인:
  - Gazebo가 정지 상태로 시작하면 센서 시뮬레이션도 멈춰 있음
- 해결:
  - `gz sim` 실행 인자에 `-r`을 넣어 기본 재생 상태로 시작하도록 수정
- 결과:
  - RGB/Depth/IMU/Odom 토픽 수신이 정상화됨

### 6.2 카메라 브리지를 하나의 `parameter_bridge`에 몰아넣었더니 전달이 불안정하던 문제

- 증상:
  - `/agribot/camera/image`, `/depth_image`, `/camera_info`가 간헐적으로 수신 실패
- 원인:
  - 이미지 토픽과 일반 메시지 토픽을 같은 방식으로 묶어서 브리지한 구성이 불안정했음
- 해결:
  - 이미지 토픽은 `ros_gz_image`
  - `camera_info`는 별도 `parameter_bridge`
  - 역할별 브리지로 분리
- 결과:
  - 카메라 계열 토픽이 안정적으로 연결됨

### 6.3 LiDAR가 안 뜨고 Gazebo 성능이 심하게 떨어지던 문제

- 증상:
  - LiDAR 토픽 미수신
  - IMU 설정 주기는 높지만 실제 시스템 응답은 매우 낮음
  - Gazebo에서 `Trimesh-trimesh contact hash table bucket overflow` 경고 반복
- 원인:
  - 온실, 식물, 토마토 모델의 triangle mesh 충돌체가 물리 부하를 크게 유발
- 해결:
  - 문제를 브리지 이슈와 물리 성능 이슈로 분리해서 봄
  - 이후 calibration world를 따로 만들고, collision 부담과 주행 검증 환경을 분리
- 결과:
  - “센서가 안 뜨는 문제”와 “시뮬레이터가 느린 문제”를 같은 문제로 보지 않고 분리 진단할 수 있게 됨

### 6.4 `/odom`은 오는데 `/tf`가 부족해서 RViz와 Nav2 해석이 꼬이던 문제

- 증상:
  - Gazebo는 `/odom`을 주는데 RViz나 `tf2`에서 바로 쓰기 어려움
  - 프레임 정합이 불안정해 후속 localization/주행에 문제 발생
- 원인:
  - `map`, `odom`, `base_link`, `camera_link`, `lidar_link`, `imu_link` 연결이 명확히 정리되지 않았음
- 해결:
  - `/odom`을 `/tf`로 재발행하는 `odom_tf_broadcaster` 추가
  - 센서 정적 TF 명시
  - 초기엔 `map -> odom`을 임시 identity로 발행
- 결과:
  - TF 트리가 정리되어 localization과 perception의 기준선이 안정화됨

### 6.5 `/cmd_vel`이 끊겨도 Gazebo DiffDrive가 마지막 명령을 유지하던 문제

- 증상:
  - teleop 종료 후에도 로봇이 계속 움직일 수 있음
- 원인:
  - Gazebo DiffDrive plugin 특성상 마지막 속도 명령 유지
- 해결:
  - `/cmd_vel` 입력을 감시하는 watchdog 노드를 추가하고 stale command는 zero twist로 변환
- 결과:
  - 제어 안전성이 올라가고 데모 중 오작동 가능성이 줄어듦

### 6.6 주행은 되는데 오도메트리 overshoot와 직진 검증이 농장 월드에서 너무 불안정하던 문제

- 증상:
  - 급가속/급회전 overshoot
  - 농장 월드에서는 충돌체가 많아 주행 성능 검증 자체가 어려움
- 해결:
  - DiffDrive 파라미터 재조정
  - `odometry_calibration_world.sdf`를 따로 만들어 순수 주행/odom 검증 환경 확보
- 결과:
  - `/odom`이 약 `50 Hz`로 안정화되고, 직진 검증도 가능해짐

### 6.7 AMCL이 잘못된 LiDAR 토픽을 보고 있어 localization이 틀어지던 문제

- 증상:
  - localization이 기대한 대로 수렴하지 않음
- 원인:
  - AMCL의 `scan_topic`과 실제 브리지 토픽이 불일치
- 해결:
  - `scan_topic`을 `/agribot/lidar/scan` 또는 현재 실제 사용 토픽 기준으로 맞춤
  - 이후 하드코딩 맵 주행 단계에서는 `/agribot/lidar` 기준도 맞춰 조정
- 결과:
  - AMCL과 실제 센서 데이터 기준이 일치하게 됨

### 6.8 하드코딩 맵 기반 주행에서 waypoint frame과 TF 기준이 섞이던 문제

- 증상:
  - waypoint가 `odom` 기준으로 잡혀 있어 정적 맵 주행과 맞지 않음
- 해결:
  - patrol waypoint frame을 `map`으로 통일
  - `map -> odom`은 AMCL이 담당하도록 구조 정리
- 결과:
  - 정적 맵 기반 데모 주행 경로가 안정화됨

### 6.9 정적 맵과 live obstacle layer가 미세하게 어긋나 planner가 통로를 막아버리던 문제

- 증상:
  - `no valid path found`
  - 실제로 빈 통로인데 costmap에서는 막힌 것으로 판단
- 원인:
  - 하드코딩 static map과 live LiDAR obstacle layer가 완전히 정렬되지 않음
- 해결:
  - 하드코딩 맵 데모 모드에서는 obstacle layer를 비활성화
  - static map + inflation 기반으로 planner/controller를 단순화
- 결과:
  - 데모 목적의 안정적인 주행이 가능해짐

### 6.10 Gazebo/bridge/Nav2를 동시에 띄우면 startup timeout으로 localization lifecycle이 멎던 문제

- 증상:
  - `map_server change_state timeout`
  - `planner_server`가 `Robot is out of bounds of the costmap!` 반복
- 원인:
  - Gazebo, bridge, Nav2가 동시에 뜰 때 초기 부하가 몰림
- 해결:
  - `simulation.launch.py`에서 navigation/localization bringup을 약간 지연
- 결과:
  - 초기 기동 성공률이 올라감

### 6.11 patrol node가 존재하지 않는 pose topic을 보고 있어서 상태 추적이 어긋나던 문제

- 증상:
  - patrol status는 살아 있는데 내부 pose 판정이 정확하지 않음
- 원인:
  - 시뮬레이션에서 `/odometry/filtered`가 없는데 그 토픽을 바라보고 있었음
- 해결:
  - simulation 환경에서는 patrol pose topic을 `/odom`으로 override
- 결과:
  - soft-complete, already-reached 같은 상태 판정이 개선됨

### 6.12 제자리 회전 시 차체가 살짝 뒤로 밀려 보이던 문제

- 증상:
  - Nav2 명령은 정상인데 Gazebo에서 뒤로 튕기는 것처럼 보임
- 원인:
  - rotate-to-heading 보정이 공격적이었고, DiffDrive 가속도/jerk 제한도 높았음
- 해결:
  - controller 파라미터와 DiffDrive 물리 파라미터를 더 보수적으로 조정
- 결과:
  - 회전 구간의 시각적 안정성이 좋아짐

### 6.13 모바일 관제 화면에서 한 화면에 맵과 대시보드가 같이 안 보이던 문제

- 증상:
  - 작은 세로 화면에서 맵 또는 대시보드 한쪽이 과하게 밀림
- 해결:
  - `412x915` 기준으로 상단 맵, 하단 대시보드가 보이도록 프론트 레이아웃 반응형 조정
- 결과:
  - 모바일 시연 시 맵과 관제 버튼을 한 화면에서 같이 보여줄 수 있게 됨

## 7. 발표 때 강조할 수 있는 포인트

### 7.1 단순 시뮬레이션이 아니라 “서비스형 로봇 파이프라인”이라는 점

- 로봇이 움직이는 것만 구현한 것이 아니라,
- `주행 -> 인식 -> 이벤트 발행 -> 백엔드 저장 -> 웹 대시보드 반영`
- 이 흐름을 끝까지 연결했다는 점이 핵심이다.

### 7.2 기술 선택이 기능별로 역할이 명확하다는 점

- ROS 2: 로봇 내부 실시간 미들웨어
- Gazebo: 실물 대체 시뮬레이터
- MQTT: 로봇과 서버 사이 경량 메시지 브로커
- FastAPI: 서비스 API와 실시간 인터페이스
- PostgreSQL: 상태/이력 저장
- React: 운영자 관제 UI

즉, 각 기술이 서로 겹치지 않고 역할이 분리되어 있다.

### 7.3 가장 큰 성과는 “문제 해결 방식”이었다는 점

- 이번 프로젝트에서 어려웠던 부분은 단순 구현보다 **통합 과정의 불안정성**이었다.
- 센서가 안 뜨는 문제, TF 정합 문제, Nav2 timeout, static map과 obstacle layer 불일치, 모바일 UI 시연성 문제까지
- 각각을 분리해서 원인-대응-검증 구조로 정리했다는 점이 엔지니어링 성과다.

## 8. 발표용 한 줄 결론

`AgriBot 프로젝트는 Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic을 기반으로 자율주행, 인식, IoT 제어, 백엔드, 관제 UI를 하나의 흐름으로 통합했고, 센서/TF/Nav2/시뮬레이터/대시보드에서 발생한 실제 문제들을 단계적으로 해결하며 데모 가능한 수준까지 안정화한 프로젝트다.`
